## 0. The run path, and the seeding method

**Recommendation: benchmark mode plus a helper mod, as the one run path for
both issues. I agree with the coordinator.** The feasibility test settles it:

- It works on 2.0.77 and 2.1.24 with `--network none`, no port, no RCON, no
  auth. That is exactly the locked-down one-off container Foreman already
  runs four kinds of (SPEC 14.3: preview, territories, resources, mod
  settings). No new Docker endpoint, no network, no RCON password, no change
  to 14.3's rules beyond naming a fifth and sixth kind.
- The game exits by itself after N ticks. No readiness wait, no stop.
- A throwaway server contacts auth.factorio.com at start, needs a network,
  and needs an RCON password in the container. All three break the
  one-off container's posture.

Rejected options, recorded so nobody re-proposes them:

| Option | Why rejected |
|---|---|
| Throwaway server plus one RCON Lua command (the issue's step 1) | Needs a network (auth.factorio.com, RCON), an RCON password inside an untrusted container, a readiness wait and a stop; strains SPEC 14.3. Its one gain, no helper mod, is small now the mod is proven. |
| Throwaway server plus helper mod, kill on output file | No RCON, but still a server lifecycle, and it reaches for the network at start. Kept only as the fallback if a future game version breaks `--benchmark`. |
| Reading `level.dat` in Go | Rejected in #769 itself: undocumented, shifts between patches. |

**The swappable piece.** Every difference between methods lives in one
function in one file, `internal/game/savecopy.go`:

```go
// saveCopyCommand is the shell script that runs the work folder's save
// with the control mod enabled, and leaves the mod's output files in the
// work folder (SPEC 8.16). It is the only place the seeding method lives.
func saveCopyCommand(m saveCopyMod) string
```

The Lua is written as a function that builds the JSON (`foreman_read()`),
called from `on_init`. If the method changed:

- to "server plus mod, kill on file": only `saveCopyCommand` changes (run
  `--start-server` in the background, wait for the file, kill). Nothing else.
- to "server plus RCON": `saveCopyCommand`, the container spec (a network),
  and one wrapper around `foreman_read()` (`/sc rcon.print(foreman_read())`).
  The output JSON, parser, record, tracking and UI do not change, because
  they depend only on the JSON contract in section 3.

### Data model and migrations

**No database migration** under the recommended storage (decision D1).
On-disk additions, which are hard to undo and so are fixed here:

- `worlds/<id>/players.json`, Foreman's record of the players of the save
  the world loads. Snapshots, restore and clone-with-save carry it with no
  code change, because a snapshot walks the whole world folder
  (`worldFiles`, `internal/world/snapshot.go`). A restore therefore brings
  back the record that matches the restored save, with its real dates.
- `factorymaps/<id>/` under the data directory (beside `previews/`): the
  kept pictures and a small `factorymap.json`. A cache: never in a world or a
  snapshot, safe to delete, keyed by world id so several worlds fit.

`players.json`, format 1 (snake_case, as `world.json`):

```json
{
  "format_version": 1,
  "basis": {"save": "_autosave3.zip", "size": 164000000, "modified": "2026-11-21T10:00:00.123456789Z"},
  "as_of": "2026-11-21T10:00:00Z",
  "seed": {"at": "2026-11-21T10:05:00Z", "save": "_autosave3.zip", "game_version": "2.0.77", "result": "ok"},
  "tracked_since": "2026-11-21T10:05:00Z",
  "inexact": false,
  "game_ticks": 84137075,
  "players": [
    {"name": "OrcScorpion", "seeded_ticks": 28484153, "tracked_seconds": 0, "last_seen": null}
  ]
}
```

- `basis` is the save the record matches. The record is valid while the
  save the world would load (`LoadTarget`) is the basis.
- `as_of` is the moment the totals are true for. Folding a session adds only
  the part after `as_of`, then moves `as_of`, so replaying log lines after a
  Foreman restart never counts a session twice.
- `seed.result` is `ok` or a failure id (`image-missing`, `out-of-memory`,
  `timeout`, `mods-differ`, `save-newer`, `bad-output`). With a failure the
  page shows "tracked since <date>" and no seeded totals.
- `inexact` is set when Foreman may have missed time (a crash, or Foreman was
  down during a run). See decision D7.
- `last_seen` is a real date from a tracked session, or null. The save's
  `last_online` and `connected` are never used: the test showed both are
  wrong for players who were online at save time.

## 3. Shared contracts (task C0 commits these as stubs)

### Helper mod output, players (`saveplayers.json`, format 1)

```json
{"format": 1, "game_version": "2.1.24", "tick": 8352001,
 "active_mods": [{"name": "base", "version": "2.1.24"}],
 "players": [{"name": "toddawhittaker", "online_ticks": 8282296}]}
```

Limits (14.6): at most 1 MiB, 10,000 players, 1,000 mods; numbers whole,
0 to 2^53; names follow the 8.2 player name rule; unknown fields refused.
Foreman compares `active_mods` (less the helper) with the world's enabled
mods and versions, and refuses the result as `mods-differ` on any
difference, because the game drops a missing mod silently and exits 0.

### Helper mod output, factory map (format 1, written to the work folder, not the tmpfs)

`factorymap/manifest.json`: `{"format":1,"game_version","tick","surfaces":[{"index","name","kind":"planet|platform|surface","chunks","min_x","min_y","max_x","max_y","file"}]}`
and one `surface-<index>.jsonl` per surface, each line `{"x","y","data"}`
where `data` is `helpers.encode_string(force.get_chunk_chart(surface, chunk))`
(the game's own 32 by 32 chart pixels). Limits: 256 MiB in total, 300
surfaces, 65,536 charted chunks per surface, each chunk's decoded data
exactly the expected size. The run's `config.ini` puts write-data in the work
folder for this kind, since the 64 MB tmpfs cannot hold it.

## 4. Behaviour the builders implement (summary of 8.14 to 8.16)

- **Seed when**: the world page (or Server page) asks for the view, the record
  is missing, does not match `LoadTarget`, or is inexact (D7), and the run is
  allowed (D2). The view returns at once with `reading`; the result arrives by
  `UpdateSavePlayers`. A seed that failed for one basis is not retried until
  the basis changes or an admin clicks "Read again". No scheduler.
- **Before the run**: `PreStartCheckAt` must report no mod or version problem;
  otherwise the record is written as tracked-only with `mods-differ` or
  `save-newer`, and no container runs.
- **Work folder**: `config.ini`, the save as a hard link mounted read-only at
  `SaveCopyMount` (a copy when the link fails, after the 6.11 space check),
  `LinkModsInto`, a **copy** of `mod-settings.dat` (the game rewrites it),
  the helper. Never `config/`, `rconpw` or `server-settings.json`.
- **After the run**: write the record only if `LoadTarget` still equals the
  basis read before (the modsettings key pattern), under the world lock.
- **Start cancels a seed** of the same world (kills its container); it is
  tried again at the next view while stopped.
- **Tracking**: on a live or replayed join and leave line, fold the session
  after `as_of`. On a save finished during a run Foreman started, `Rebase` to
  that save. At a stop or crash, close open sessions at Docker's FinishedAt
  and fold. A crash or a re-attach sets `inexact`.
- **Game time**: while running, `/time` (never Lua) at most once a minute when
  a page asks, and at each finished save; `SetGameTicks` from it. Stopped:
  the record. Use `game.tick` from the seed, since `/time` reports
  `game.tick` (tested: 276 h 40 min equals tick 59,760,005).
- **Upload** of a save removes the record (`RemovePlayersRecord`), since its
  mtime could fall inside a run window and pass as the game's own save.
- **Mod runs (ADR 0014)**: leave `players.json` out of the mod-run file list,
  so a seed between two mod changes does not cost an extra snapshot.

## 6. Decisions for Todd

**D1. Where the players record lives** (hard to undo: on-disk layout).
1. *`worlds/<id>/players.json` (recommended).* Gains: plain file (vision
   principle 4); snapshots, restore and clone carry it for free, so a restore
   brings back the matching record with real dates and needs no re-seed.
   Costs: the game container can write the world folder, so the file is
   untrusted input (parsed under limits; a tampered file only lies about play
   times); it adds a small file to every snapshot.
2. *A database table (migration 0013).* Gains: out of the game's reach.
   Costs: game data in the database, against principle 4; a restore cannot
   bring back the matching record, so every restore re-seeds and loses
   tracked dates.

**D2. When a seed may run.** Measured peak memory: 0.4 GB (tiny), 1.5 GB
(32 MB save), 2.8 GB (94 MB), 6.9 GB (187 MB with 44 mods), 1 to 44 s.
1. *Automatically while the world is stopped, and while it runs only when an
   admin clicks "Read players from the newest save", which states the memory
   it may take (recommended).* Gains: no surprise memory spike beside a live
   game; an always-running world is seeded with one click, once. Costs: one
   click on an always-running world.
2. *Only while stopped.* Gains: simplest and safest. Costs: a world that
   never stops (the family base) never gets its history.
3. *Also automatically beside a running game when `/proc/meminfo` shows
   enough free.* Gains: no click. Costs: a second game's memory next to a
   live one, and a misread (remote Docker) can get the live game killed by
   the kernel, losing play since its last autosave (principle 1).

**D3. Where the player list shows.**
1. *The full list on the world's Overview page; the Server page shows total
   play time and a "N players in this save" link to it (recommended).*
   Gains: works for stopped and inactive worlds; the Server page stays short;
   one click from the Server page. Costs: one click to see offline players.
2. *Full list on the Server page only.* Gains: zero clicks for the live
   world. Costs: no list for other worlds; a long list on a phone page.
3. *Both, in full.* Gains: no click anywhere. Costs: two renderings to keep
   in step, a longer Server page.

**D4. #773 in this batch.**
1. *Cut down: one PNG per surface from the game's own chart (it already
   draws buildings as the in-game map does), shown and downloadable on a
   world "Factory map" page; no outline overlay, no zoom viewer
   (recommended).* Gains: reuses the whole run path; about six small tasks.
   Costs: no category overlay; plain picture scrolling; needs game 2.0.61 or
   later (1.1 worlds get "not supported").
2. *Full: chart plus building outlines by category plus a zoomable viewer.*
   Gains: the issue as written. Costs: an entity dump (a big save has
   463,000 entities on Nauvis) with its own limits, an overlay renderer and
   a viewer; doubles the batch.
3. *Defer #773; build only #769 on the shared path.* Gains: smallest batch.
   Costs: the run path is proven only for players until later.

**D5. #773 modes.**
1. *Manual only: a "Draw factory map" button, kept until the save changes
   (recommended).* Gains: no background memory use. Costs: a click.
2. *Automatic after each graceful stop, plus manual.* Gains: always fresh.
   Costs: up to a minute and several GB at every stop, also during switches
   and nightly restarts.
3. *Automatic, manual or off as a setting, with "skip while players are
   online" (Tricade's).* Gains: flexible. Costs: a setting and a schedule;
   "skip while online" only matters if runs happen beside a live game,
   which D2 option 1 already rules out.

**D6. Factory map beside a running game.** Follow D2 (recommended: on a
click, with the memory warning), or stopped only.

**D7. Correcting drift.** A crash or Foreman downtime can miss minutes.
1. *Mark the record inexact and re-seed automatically at the next view while
   the world is stopped, plus a "Read again" button (recommended).* Gains:
   self-correcting, rare runs. Costs: an occasional run.
2. *Only the button.* Gains: no unprompted runs. Costs: drift stays until
   someone notices.

**D8. Memory limit of the run.**
1. *A fixed 12 GiB, time limit 5 minutes (recommended).* Gains: fits the
   largest measured save (6.9 GB) with room; a smaller host kills the run
   itself, which fails safe while the game is stopped. Costs: a large cap on
   a host that also runs other things.
2. *A fixed 8 GiB.* Gains: tighter. Costs: 16% over today's largest save;
   a growing base fails to seed soon.
3. *An app setting.* Gains: the operator decides. Costs: a setting nobody
   knows how to choose.

**D9. Priorities.** 8.14, 8.15 and 8.16 as P1, 5.13 as P2 (recommended,
the issue says "probably P2"); or 5.13 as P1 if Todd wants it in v1.

## 7. Risks

- **Memory.** A run takes about as much as running the save (6.9 GB at
  187 MB with heavy mods; mod loading took 27 of 44 s). D2 and D8 contain
  it. The run shares the one preview slot, so a long seed makes a map
  preview on the Generate page wait and then say "busy"; accepted, as the
  mod settings run (5 minutes) already does.
- **The original save never changes.** Three layers: the game never writes a
  save in benchmark mode (hashes identical in every test run); the save is
  mounted read-only over its link, so the kernel refuses a write; the work
  folder never holds the world's `mod-list.json` or `mod-settings.dat`, only
  copies (the game rewrites both). Tests:
  - unit (A1): the container spec holds a read-only mount at
    `SaveCopyMount` whose source is the work folder's link; no bind source
    is inside `worlds/`; the work folder holds copies (different inode) of
    `mod-list.json` and `mod-settings.dat`;
  - unit (A4): SHA-256, size, modification time to the nanosecond and inode
    of every file in the world folder are the same before and after a seed
    against the fake, except `players.json`;
  - real game (A12, 2.0.77 and 2.1.24, and 1.1.110 if benchmark runs there):
    the same whole-folder check after a real seed, and a hostile run of the
    same container spec with `sh -c 'echo x >> save.zip'` that must fail and
    leave the hash unchanged.
- **Silent mod loss.** The game drops missing mods and exits 0, so a wrong
  mod set would give plausible numbers from a different game. The pre-start
  check runs first, and `active_mods` is compared after.
- **Game version drift.** `--benchmark` flags, `info.json` per line
  (`modInfo`), `helpers` against 1.1's `game` (copy `local h = helpers or
  game` from `resources/control.lua`), `get_chunk_chart` only from 2.0.61,
  and `/time`'s English wording. Each fails safe to "tracked since" or "not
  supported". A12 and F6 run on each pinned line; `/time`'s parser refuses
  any form it does not know rather than guess.
- **`connected` and `last_online` are wrong** in benchmark mode for players
  online at save time; neither is read.
- **Secrets.** Nothing secret enters the run: no `config/`, no `rconpw`, no
  game password, no RCON. Player names are untrusted (escaped by templates;
  marked untrusted if MCP ever lists them). The failed run's log tail
  (`previewLog`) is never shown. `players.json` holds no secret.
- **Disk.** The save is a hard link (no space). The copy fallback costs the
  save's size and must pass the 6.11 reserve check. Factory map output (tens
  of MB) lives in the work folder and is deleted with it.
- **The record file is in the game's reach.** Parsed under limits; a newer
  `format_version` is shown but not rewritten, as `world.json` is.

## 8. Left out

- The MCP and REST `list_players` tool keeps returning players online now.
  Adding save players later is an optional field, allowed within `/api/v1/`
  (23.7), so it is easy to add when asked.
- A session history list per player: only totals and last seen are kept, so
  the file cannot grow without limit.
- Building outlines by category and a zoom viewer for #773 (D4 option 2).
- Any scheduler or background loop for seeding: seeds start from a page view.
- Several worlds at once: nothing here assumes one. The record and cache are
  per world id, and the run takes the world id.
